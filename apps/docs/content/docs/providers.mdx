Multica works with 31 AI coding tools. It does not replace the tool you use: a runtime invokes the tool already installed and signed in on the computer, then writes progress and results back to the issue. If you already use one of these tools, you can usually keep it, and different agents in one workspace can use different tools. If you have not picked one yet, weigh four things:

For guidance on picking a tool when creating an agent, see [Creating and configuring agents](/agents-create).

- whether it is already installed on the computer;
- which models your account can use;
- whether Multica needs to configure MCP for it;
- which skills the team wants to reuse.

Install steps are in [Install AI coding tools](/install-agent-runtime).

## What each tool is for

From Google. CLI binary name is `agy`. Pairs with Google's Antigravity service and ships with a Gemini-backed default model. Multica launches Antigravity with `agy -p` because that is the daemon-compatible non-interactive mode; `agy -i` needs an attached TTY and is not suitable for background task execution. Current Antigravity CLI releases can still execute tools from this mode, but stdout is plain assistant text rather than a structured event stream, so Multica relays the transcript as text and cannot show per-tool telemetry for Antigravity today. **Session resumption works** via `--conversation <id>`; the daemon captures the conversation UUID from the CLI's log file. **Model selection works** via the `--model` flag (added in agy 1.0.6): the daemon enumerates the catalog with `agy models` and ships the chosen value verbatim. Note these are human display strings such as `Claude Opus 4.6 (Thinking)`, not `provider/model` slugs — and agy silently no-ops on a value it doesn't recognise, so prefer picking from the discovered list over typing a custom one. Skills land in `.agents/skills/` (the CLI inherits Gemini CLI's workspace skill layout — see [Antigravity migration docs](https://antigravity.google/docs/gcli-migration)).

For Claude Code, Multica lists and imports user and plugin skills from an absolute `CLAUDE_CONFIG_DIR` set in the daemon environment. Paths set only inside a launch wrapper are not visible to the scanner.

For Amp, the model field selects an Amp **mode**, such as `high`, rather than an underlying model ID. Leave it empty to use Amp’s default.

Amp also requires `AMP_API_KEY` in the daemon or agent environment; a saved interactive login alone is not enough.

"Multica-managed MCP" means you can define MCP servers in the agent configuration and Multica passes them to the tool before a run. The column only says whether Multica can configure it for you, not whether the tool has other ways to configure MCP.

Tools with — under "Model picked in Multica" take their model from their own configuration; see [Model sources](#model-sources).

Devin supports stdio MCP servers; HTTP/SSE entries are passed only if the CLI advertises support. Devin skills are imported from `$XDG_CONFIG_HOME/devin/skills` (default `~/.config/devin/skills`) or `%APPDATA%\devin\skills` on Windows, then the legacy `cognition/skills` root, then `~/.codeium/<channel>/skills` (`windsurf`, `windsurf-next`, `windsurf-insiders`, in that order), and finally `~/.agents/skills`. On duplicate skill keys, the first root wins for both listing and import.

### Claude Code

From Anthropic. **First choice for new users** — the most complete feature set: session resumption actually works, it reads MCP configuration, and it supports fine-tuning flags like `--max-turns` and `--append-system-prompt`. Requires an Anthropic API key.

### CodeBuddy

From Tencent. A Claude Code–compatible CLI agent — Multica drives it with the same stream-json protocol as Claude Code, so session resumption works (via `--resume`) and MCP config is passed through `--mcp-config`. CodeBuddy ships its own native config directory rather than reusing Claude's, so skills land in `.codebuddy/skills/` and the runtime brief is written to `CODEBUDDY.md`. Models are discovered dynamically.

## Connect a tool

Every tool in the table connects the same way: the Multica daemon on a computer looks up each tool's command on `PATH` and registers one runtime per tool it finds. Runs execute on that computer, with the tool's own login and subscription; Multica does not ship the tools or proxy their model calls.

1. Install the tool and sign in to it, the way its own docs describe.
2. On the same computer, open [Multica Desktop](/desktop-app), which connects the computer automatically, or install the CLI and start the daemon:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
   multica setup
   ```

   On Windows, use `irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex` for the first line. Self-hosted instances use the commands in the [Self-host quickstart](/self-host-quickstart).
3. Check that the tool shows up as a runtime under that computer on the **Runtimes** page, or with `multica runtime list`. After installing another tool, run `multica daemon restart` or reopen Desktop.
4. [Create an agent](/agents-create) on that runtime and assign it an issue.

If the tool is installed somewhere the daemon's `PATH` does not reach, point `MULTICA_<PREFIX>_PATH` at it; see [Environment variables](/environment-variables#daemon-configuration). One computer can host several tools, and a workspace can mix computers, so a team can run Claude Code on one machine and Codex or Kimi on another from the same board.

## Steer a running run

You can [add a message to a run that is still working](/mentioning-agents#steer-a-running-agent) instead of waiting for the next run. This needs support from the AI coding tool, and from these versions on:

| Tool | Minimum version |
|---|---|
| Antigravity | 1.4.8 |
| Claude Code | 2.1.110 |
| Codex | 0.100.0 |
| Cursor Agent | 2026.10.14 |
| Grok | 1.0.14 |
| Kiro CLI | 2.33.0 |
| Pi | 1.4.0 |

With other tools or older versions, **Add to current run** is not offered: a reply is handled in a new run after the current one, or you stop the current run and start over.

## Model sources

When you create an agent, the model list comes from the corresponding runtime. Some tools expose a fixed set of model names; others return available models based on local configuration, the signed-in account, and subscription entitlements.

If you do not pick a model, Multica uses the tool's own default. If the list is empty, confirm the runtime is online and the tool is signed in, then refresh the model list.

For Kiro CLI, the **Thinking** picker in agent creation and settings lists the effort levels advertised for the selected model. The choice applies to new and resumed sessions. Leave it unset to use Kiro's own effort setting. Models or CLI versions that return no effort options keep the picker hidden.

Devin's picker lists the model choices advertised by its ACP session. Choose a canonical model ID, an unambiguous session model name or catalog family slug/alias (such as `opus`), or leave the model empty for the CLI default. Family aliases that require `devin models list` can still require a saved CLI login; if alias resolution fails, select a model ID from the picker. Multica confirms the actual session model before sending the prompt; a fallback to another family is rejected. Ambiguous names, arbitrary partial names, or unavailable variants require a canonical ID rather than a guessed match. Usage is attributed to the reported model, not the launch flag. Adaptive usage stays under the reported Adaptive routing ID, not an inferred underlying model.

Devin reads `WINDSURF_API_KEY` when set, otherwise the login saved by `devin auth login`; unknown ACP auth methods do not block that stored login. Model discovery uses the daemon user's credentials: a key set only in an agent's custom environment is unavailable to the runtime model picker. An empty session model list prompts you to check those credentials and your team's model allowlist. Multica preserves Devin's configured session mode rather than raising permissions. If it defaults to `plan`, switch to an editing mode in Devin before dispatching work that must change files.

QwenPaw, MiniMax Code, and ZeroClaw are exceptions: they do not accept a model chosen from Multica, so the picker is inert and shows "Managed by runtime". Choose the model in the tool's own configuration instead. An empty model list for these tools is expected and does not mean the runtime is offline.

For Antigravity, use the model picker to select the exact reasoning variant shown by `agy models`, including any suffix. Multica has no separate **Thinking** setting for Antigravity. If you pass `--effort` in custom arguments, Antigravity checks whether it can be combined with the selected model.

DeepSeek Harness advertises its model catalog from the runtime itself (`dsh --profile multica --list-models`). Its model ids use the `provider/model` form (for example `deepseek-official/deepseek-chat`), so select the full id from the list.

<Callout type="info">
Model names are not shared across tools. After switching AI coding tools, the previous model value is invalid in the new tool and needs to be selected again.
</Callout>

### Codex

Tools marked ✓ can continue an existing session in a later run, provided the original session still exists and the run is executed by a runtime that can reach it. MiniMax Code 0.1.2 advertises no session-loading capability over ACP, so Multica starts a fresh MCode session for a later run.

Multica stores the session identifier the tool returns. The next time work continues on the same issue, the runtime tries to resume that session; if it cannot, it starts a new session and keeps going. Pi stores a local session file path, so it depends more on the original computer and file.

Retry and session-resumption rules are in [Runs](/tasks#manual-retry).

### Cursor

From Anysphere, the CLI counterpart to the Cursor editor. **Session resumption works** with current Cursor Agent releases: the stream-json event includes a `session_id`, and Multica passes it back with `--resume <id>` on the next run. MCP config is materialized into the task workspace's `.cursor/mcp.json`, with Cursor's project approval file written under a per-task `CURSOR_DATA_DIR` so managed MCP servers do not depend on the user's global Cursor approvals.

### Hermes

From Nous Research. Uses the ACP protocol (shares a transport with Kimi). Session resumption works, and MCP config is passed through ACP `mcpServers`. Hermes discovers skills only from its home directory (`~/.hermes/skills/`, or `%LOCALAPPDATA%\hermes\skills\` on native Windows) and configured `skills.external_dirs` — it has no workspace-relative discovery. So **when an agent has skills assigned**, Multica points `HERMES_HOME` at a per-task overlay of your Hermes home: your real home is mirrored by symlink (auth/secrets included, so token refreshes propagate), a derived `config.yaml` references your existing skills as read-only external roots, and only the assigned skills are written into its `skills/` directory — where they take precedence, so your global skills keep working. A `-p`/`--profile` selection in `custom_args` is honored: the overlay is seeded from that profile's home, and the flag is consumed from the launch command so it can't slip past the overlay. Multica never writes to your shared home directly (it only reads it and links into it), though writes Hermes itself makes through a mirrored symlink — a token refresh, say — do propagate. Task memory is isolated per task: a fresh `memories/` directory, plus the external `memory.provider` backend is disabled in the derived config, so neither on-disk notes nor a shared Supermemory/Hindsight-style bank crosses between tasks (a managed, agent-scoped memory backend is a separate future decision). The SQLite `state.db` session store and its journal files are task-local too: Hermes creates them inside the overlay, so host conversation history is neither linked nor copied and a live Windows WAL lock cannot block setup. A Hermes task with no assigned skills runs against your real home unchanged.

**Selecting a Hermes profile.** To launch Hermes under a specific profile, set the agent's `custom_args` to the profile flag and the profile name as two separate entries — for example, for a profile named `research`:

```json
["-p", "research"]
```

Don't combine them into one string like `"-p research"`; Multica passes each array item as a separate argv entry. `custom_args` is configured per agent — see [Creating and configuring agents](/agents-create).

### Kimi

From Moonshot, aimed at the Chinese market. Shares the ACP protocol with Hermes, including MCP config through ACP `mcpServers`, but the skill path `.kimi/skills/` is Kimi CLI's native discovery mechanism — different from Hermes's fallback.

### Kiro CLI

From Amazon. Uses ACP over stdio via `kiro-cli acp`. Session resumption works through ACP `session/load`, MCP config is passed through ACP `mcpServers`, model selection works through `session/set_model`, and skills are copied into `.kiro/skills/` for native project-level discovery.

### OpenCode

From SST, open source. Dynamically discovers available models and model variants (scans the CLI's configuration file). Session resumption works, and it consumes the agent's `mcp_config` field — Multica injects it inline through the `OPENCODE_CONFIG_CONTENT` environment variable, so the agent's MCP servers reach OpenCode without writing anything into the task workdir's `opencode.json` (the agent or the user keep ownership of that file). When a model exposes variants, Multica shows them as the agent thinking selector and passes the selected value through `opencode run --variant`. **Suitable for tinkerers who want to customize their model catalog.**

### DevEco Code

**DevEco Code** is Huawei's independent coding agent for HarmonyOS development (`deveco` CLI, [gitcode.com/openharmony-sig/deveco-code](https://gitcode.com/openharmony-sig/deveco-code)). Built on the OpenCode engine, it ships as a complete product in its own right — its own model catalog and provider (the built-in `deveco/GLM-5.1`), Huawei-account auth, and its own config and skill layout under `~/.config/deveco/` and `.deveco/skills/`. Multica drives it over `deveco run --format json`, parsing the NDJSON event stream. **Session resumption works** (`--session <id>`), models are discovered dynamically (`deveco models`), and system context is delivered through the per-task `AGENTS.md`. MCP servers are configured through DevEco's native `DEVECO_CONFIG_CONTENT` channel; Multica-side `mcp_config` wiring is in progress, so the MCP tab is hidden for DevEco agents for now. Authenticate with `deveco auth login` (Huawei account).

### OpenClaw

Open-source project, a CLI agent orchestrator. MCP config is materialized through Multica's per-task OpenClaw config wrapper. **Model is bound at the agent layer** (`openclaw agents add --model`) — it can't be overridden per task. Configuration is strictly controlled: users can't pass `--model` or `--system-prompt`; the agent-registration config decides.

### Pi

From Inflection AI, minimalist. **Session resumption is unusual** — the session ID is a file path on disk (`~/.pi/...`) rather than a string ID. In other tools, the resume id is a string returned by the CLI; in Pi, the resume id is the session file itself.

### OMP

[Oh My Pi](https://omp.sh) is a standalone coding agent, **not a Pi alias**. Multica launches it non-interactively as `omp -p --mode json --session-dir <dir>`, reads its Pi-compatible JSON event stream, and saves the emitted string session ID for `--resume <id>` on the next task. Models and their supported thinking levels are discovered from `omp models --no-extensions --json`; Multica sends the selected model selector with `--model` and the selected level with `--thinking`. Assigned workspace skills are written to `.omp/skills/` for OMP's native discovery.

To enable OMP, install and authenticate it first, then make `omp` available on the daemon's `PATH` or set `MULTICA_OMP_PATH` to its absolute executable path. Restart or refresh the daemon so it detects the runtime. Set `MULTICA_OMP_MODEL` to an OMP selector to choose a daemon-wide default, or choose a discovered selector for an individual agent. OMP currently ignores an agent's `mcp_config`.

Self-hosted upgrades must apply migration `585_runtime_profile_restore_omp_after_muse` so both OMP (`omp`) and Muse (`muse`) remain available as custom runtime profile protocol families.

### Qoder

From Alibaba. An agentic coding CLI. Uses the ACP protocol over stdio (shares a transport with Hermes, Kimi, and Kiro CLI). Session resumption works through ACP `session/resume`, MCP config is passed through ACP `mcpServers`, model selection is discovered dynamically, and skills are copied into `.qoder/skills/` for native discovery.

### Qwen Code

From Alibaba. Multica drives Qwen Code with its native non-interactive JSONL protocol, `qwen -p <prompt> --output-format stream-json --yolo`, and maps text, thinking, tool calls, tool results, session IDs, status, errors, and token usage into the normal task stream. Multica owns `--yolo` for unattended runs so shell, edit, and write tools remain available without an approval UI. This does not enable Qwen's sandbox: unless the deployment explicitly enables `--sandbox` or `QWEN_SANDBOX`, tools run with the daemon OS user's permissions and credential scope. Use `--exclude-tools` in custom arguments to hard-deny specific tools. **Session resumption works** through `--resume <id>`. The per-task runtime brief is written to `QWEN.md`; assigned skills are copied to `.qwen/skills/`; user skills are read from `$QWEN_HOME/skills/` (default `~/.qwen/skills/`). Select a default model with `MULTICA_QWEN_MODEL` or set a manual per-task value through Qwen's `--model` flag; Multica does not advertise an account-specific static catalog. A managed `mcp_config` is materialized into a 0600 temporary JSON file and passed as `--mcp-config <path>`, which Qwen gives highest precedence for that run; the file is removed when the process exits. Leave the field null to inherit native Qwen Code MCP settings.

### Trae

From ByteDance — the official **TRAE CLI** (`traecli`, documented at [docs.trae.cn/cli](https://docs.trae.cn/cli); this is the product paired with the Trae IDE, **not** the open-source `bytedance/trae-agent`). traecli is ACP-native, so Multica drives it over the standard ACP JSON-RPC transport via `traecli acp serve --yolo`, exactly like Kiro and Qoder — `--yolo` puts it in bypass-permissions mode so headless runs don't block on tool-approval prompts.

- **Session resumption works** through ACP `session/load` (traecli advertises `loadSession: true` from `initialize`).
- **Model selection is dynamic**: the model catalog is discovered from `session/new` (`models.availableModels`) and switched per task via `session/set_model`. Set the daemon-wide default with `MULTICA_TRAECLI_MODEL`.
- **MCP is supported** — config is passed through ACP `mcpServers`; traecli advertises `mcpCapabilities: {http, sse}`, and unsupported transports are filtered out before `session/new`.
- **Authentication** is traecli's own enterprise login: run `traecli` once interactively to complete the browser login (the token persists in `~/.trae` + the OS keyring). The IDE login is separate — logging into the Trae IDE does **not** log in the CLI.
- **Skills** are written to `.traecli/skills/` (project) for native discovery; global skills live in `~/.traecli/skills`.
- The Multica runtime brief is also inlined into the prompt (traecli has no `--system-prompt` flag and reads project rules from `.trae/rules/`, not `AGENTS.md`), so the workflow instructions reach the agent regardless.

> The capabilities above were captured from the real `traecli` v0.120.42 binary: `initialize` → `loadSession:true` + `mcpCapabilities{http,sse}`; `session/new` → `result.sessionId` + `models.availableModels`; `session/prompt` streams `session/update` notifications with `sessionUpdate: agent_message_chunk`.

### Grok

From xAI. CLI binary name is `grok` (Grok Build CLI, often installed to `~/.grok/bin/grok`). Multica drives it over **ACP** via `grok --no-auto-update agent --always-approve stdio`, reusing the same transport as Trae / Kimi / Kiro / Qoder. After `initialize`, Multica chooses only an auth method the CLI advertised (`xai.api_key` when `XAI_API_KEY` is set and offered, otherwise `cached_token`) and waits for `authenticate` to succeed before any session operation; an empty or unsupported method list fails explicitly. **Session resumption works** through ACP `session/load`. **Model selection works** via the catalog returned from `session/new` and `session/set_model`. For `grok-4.5`, **reasoning effort** exposes only xAI's documented `low`, `medium`, and `high`.

### MiniMax Code

From MiniMax. An ACP-native coding agent (`mcode` CLI). MCP config is passed through ACP `mcpServers`, and skills are written to `.minimax/skills/` for native discovery. Model selection is managed by the runtime: the picker is inert and shows "Managed by runtime" (see [Model selection](#codebuddy) above). MiniMax Code 0.1.2 advertises no session-loading capability over ACP, so Multica starts a fresh MCode session for a later run.

## Session resumption: who really supports it

The session resumption mechanism is covered in [Tasks](/tasks#manual-retry). **Every supported tool resumes sessions** — pass the resume id and the task continues from the previous context. The one quirk is Pi, whose resume id is a session file path on disk rather than a string id (see [Pi](#pi) above).

## MCP configuration: provider-specific support

**Of the 31 tools, 22 consume `mcp_config`: CodeArts, Claude Code, CodeBuddy, Codex, Cursor Agent, DeepSeek Harness, Devin, Dim, Grok, Hermes, Kimi CLI, Kiro CLI, MiniMax Code, OpenClaw, OpenCode, Pi, Qoder CLI, Qoder CN CLI, Qwen Code, Reasonix, Trae CLI, and ZCode**. The other nine (Amp, Antigravity, GitHub Copilot CLI, DevEco Code, Factory Droid, Muse Code, OMP, QwenPaw, and ZeroClaw) do not read an agent's MCP configuration, so it has no effect for those tools.

The runtime paths are provider-specific: Claude Code, CodeBuddy, and Qwen Code receive it through daemon-owned temporary JSON files passed with `--mcp-config` (mode `0600` on POSIX systems because MCP configs may embed API tokens); Claude Code and CodeBuddy additionally use `--strict-mcp-config`; Codex writes a daemon-managed `mcp_servers` block into the per-task `$CODEX_HOME/config.toml`; Cursor writes `.cursor/mcp.json` plus per-task project approvals under `CURSOR_DATA_DIR`; Hermes, Kimi, Kiro CLI, Qoder, Trae, Grok, and MiniMax Code receive ACP `mcpServers`; OpenCode receives inline config through `OPENCODE_CONFIG_CONTENT`; OpenClaw receives `mcp.servers` through Multica's per-task config wrapper. OpenCode's path does **not** rewrite the project's `opencode.json`.
Amp, Factory Droid, Antigravity, GitHub Copilot CLI, DevEco Code, Muse Code, and ZeroClaw do not read the MCP configuration on an agent yet, so the field is not shown when creating agents for them.

Managed MCP delivery for Pi requires Pi 0.99.0 or later. Older Pi versions continue to run agents that have no MCP configuration.

<Callout type="warning">
MCP server commands, arguments, and environment variables are saved server-side with the agent configuration. Do not write local credentials you have no need to share into the configuration.
</Callout>

<Callout type="warning">
If you set `mcp_config` in an agent configuration but pick a tool not marked ✅ in the MCP column, your MCP servers have no effect on that agent's runtime.
</Callout>


Servers already configured on the runtime's machine are merged with the agent's configuration on that machine; see [Local MCP configuration](/daemon-runtimes#local-mcp).

## Skill injection

Before a run starts, Multica writes the skills bound to the agent into the paths in the table above, where each tool discovers them through its own native mechanism.

Skills that already exist in the repository are never overwritten. On a name collision, Multica uses a different directory name for the injected copy; after the run, it cleans up only the files it created.

- Codex uses a per-run `CODEX_HOME`, so skills are never written into the system-level Codex directory.
- Hermes uses a per-run `HERMES_HOME`. Existing local configuration is still readable, but bound skills and session data are isolated per run. This isolation kicks in only when the agent has skills bound; runs without bound skills use the machine's original Hermes home.
- OpenClaw uses `skills/` under the current run's working directory, and the per-run configuration sets that directory as the workspace.

## ZCode

ZCode uses its native NDJSON `app-server` protocol for session creation, resumption, cancellation, model discovery, thinking levels, and MCP. Tasks run in yolo mode without interactive tool approval. Reasoning choices come from the runtime model catalog; creating an agent preserves the selected model's default level.

On macOS the daemon also discovers ZCode Desktop's bundled CLI; Node.js must be installed. On Linux it discovers ZCode Desktop and runs the bundled CLI without opening a desktop window; no separate Node.js installation or manual environment configuration is needed. Enabled desktop API-key/Coding Plan connections are imported into a process-private temporary provider configuration, which is removed on exit without changing the original files. Start Plan identity tokens are not API keys and this account-authentication path is not supported. Configure a working API connection in ZCode Desktop if discovery returns no models.
