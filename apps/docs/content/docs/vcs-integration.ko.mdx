<Callout type="warn">
**자체 배포한 Multica에서만 사용할 수 있습니다.** 이 연동은 Multica를 직접 배포해 운영할 때만 제공되며 Multica Cloud에서는 사용할 수 없습니다. 자체 배포는 보통 Multica가 내부 네트워크의 Git 인스턴스에 접근하게 하려는 목적입니다. 서버에서 `MULTICA_VCS_INTEGRATION_ENABLED=true`를 켜고 `MULTICA_VCS_SECRET_KEY`를 설정해야 하며, 그전에는 **설정 → 코드**에 이 행이 표시되지 않습니다.
</Callout>

Multica는 **설정 → 코드 → Code hosting**의 워크스페이스별 **셀프 호스팅 Git** 항목에서 Forgejo, Gitea, GitLab에 연결합니다. 한 워크스페이스에서 여러 GitLab 인스턴스를 연결하고 각 인스턴스에 여러 프로젝트를 추가할 수 있습니다. 다른 워크스페이스가 같은 GitLab 인스턴스에 연결해도 연결, token, 프로젝트 목록은 별도로 관리됩니다.

브랜치 이름이나 제목에 태스크 번호(예: `MUL-123`)가 있거나 본문에서 종료 키워드 바로 뒤에 태스크 번호(`Closes MUL-123`)가 있는 Pull Request(GitLab에서는 Merge Request)는 해당 [태스크](/issues)에 자동 연결되어 태스크 사이드바의 **Pull requests**에 표시됩니다. 연결된 PR이 모두 merge되면 태스크가 워크스페이스에서 선택한 상태(기본값 완료)로 이동합니다. 카드에는 현재 head의 CI 상태가 표시됩니다.

워크스페이스 소유자와 관리자가 연결 및 프로젝트 바인딩을 관리합니다. 멤버는 워크스페이스에서 허용된 GitLab 프로젝트와 MR만 읽을 수 있으며, 자격 증명과 프로젝트 접근 권한은 워크스페이스 간 공유되지 않습니다.

<Callout type="info">
GitLab에는 App 모델이 없습니다. 워크스페이스마다 인스턴스 URL과 액세스 token을 별도로 저장하고 해당 연결에 GitLab 프로젝트를 추가합니다. token과 Webhook secret은 암호화되어 저장됩니다.
</Callout>

## 사전 조건(서버)

먼저 이 배포에서 연동을 켭니다. 기본값은 꺼짐이며 활성화하기 전에는 해당 영역이 표시되지 않습니다.

```sh
MULTICA_VCS_INTEGRATION_ENABLED=true
```

공식 자체 호스팅 `docker compose` 파일(`docker-compose.selfhost.yml`)에는 이미 설정되어 있습니다.

그런 다음 서버가 저장된 자격 증명을 암호화할 수 있도록 base64로 인코딩한 32바이트 키를 설정합니다. 설정하지 않으면 연결 양식을 사용할 수 없습니다.

```sh
openssl rand -base64 32
```

```sh
MULTICA_VCS_SECRET_KEY=<base64 32바이트 키>
```

두 값이 모두 필요합니다. 스위치는 기능을 제공할지 결정하고 키는 저장된 token과 Webhook secret을 암호화합니다. 연결, Webhook, 교체 모두 두 설정을 함께 요구합니다.

`MULTICA_PUBLIC_URL`을 서버의 공개 base URL로 설정하면 Multica가 바로 붙여 넣을 수 있는 Webhook URL을 표시합니다. 설정하지 않으면 화면에 Webhook 경로만 표시되므로 origin을 직접 앞에 붙여야 합니다.

## 워크스페이스 연결

<Steps>
<Step>
저장소를 읽을 수 있는 권한이 있는 액세스 token을 Git 호스팅 서비스에서 만듭니다.

- **Forgejo / Gitea**: 설정 → 애플리케이션에서 애플리케이션 token을 만듭니다.
- **GitLab**: `read_api` scope의 개인, 그룹 또는 프로젝트 액세스 token으로 프로젝트와 MR을 읽을 수 있습니다. Multica가 프로젝트 Webhook을 만들거나 수정하려면 `api` scope와 해당 프로젝트 Webhook을 관리할 수 있는 GitLab 역할(보통 Maintainer 또는 Owner)이 필요합니다. `read_api`만 있는 token으로는 Hook을 관리할 수 없습니다.
</Step>
<Step>
Multica에서 **설정 → 코드 → Code hosting**을 열고 **셀프 호스팅 Git** 항목에서 연결합니다. GitLab 연결은 현재 워크스페이스에 속합니다. 같은 인스턴스를 사용하더라도 다른 워크스페이스에서는 별도로 연결해야 합니다.
</Step>
<Step>
제공자를 선택하고 인스턴스 base URL(하위 경로가 있으면 포함)과 액세스 token을 입력합니다. Multica는 저장 전에 token을 검증합니다. GitLab은 연결 아래에 전체 group/subgroup/project 경로나 프로젝트 URL로 프로젝트를 추가합니다.
</Step>
<Step>
GitLab 프로젝트를 추가하면 Multica가 프로젝트 Webhook 생성을 시도합니다. 각 프로젝트의 Hook 상태와 실패 이유를 확인하세요. Multica가 Hook을 관리할 수 없다면 권한 있는 GitLab 관리자가 Multica에 표시된 URL과 secret으로 직접 설정합니다. Forgejo/Gitea는 아래 안내대로 Multica가 표시하는 Webhook URL과 secret을 등록하세요.
</Step>
</Steps>

<Callout type="warn">
액세스 token과 Webhook secret은 자격 증명으로 취급하세요. Multica가 Webhook secret을 표시할 때 저장하세요. 일반 API 응답과 로그에는 포함되지 않습니다.
</Callout>

### 사설 CA를 사용하는 인스턴스

**연결** 시 제공자 인증서에 대해 "is signed by a certificate authority this server does not trust"라는 메시지가 나오면, 인스턴스의 HTTPS 인증서가 Multica 서버가 신뢰하지 않는 내부 CA로 발급되었거나 자체 서명된 것입니다. 서버 관리자가 해당 CA를 백엔드 신뢰 저장소에 추가해야 합니다. Helm에서는 `backend.extraCACerts.configMap`을 설정하고, Docker Compose에서는 CA를 마운트한 뒤 `SSL_CERT_DIR`을 설정합니다. 자세한 절차는 [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional)를 참고하세요. 백엔드는 이 CA를 데몬에도 전달하므로, 데몬의 git도 같은 인스턴스의 저장소를 클론할 수 있습니다.

연결 요청에는 액세스 token이 포함되므로 Multica는 인증서 검증을 건너뛰는 옵션을 제공하지 않습니다. 인증서가 호스트 이름과 일치하지 않거나 검증에 실패했다는(예: 만료) 메시지가 나오면 인증서 자체를 고쳐야 합니다. CA를 신뢰하는 것으로는 해결되지 않습니다.

## Webhook 등록

저장소에 등록합니다. 모든 저장소를 포함하려면 조직이나 그룹에 등록합니다.

<Tabs items={["Forgejo / Gitea", "GitLab"]}>
<Tab value="Forgejo / Gitea" id="forgejo-gitea">

설정 → Webhook → Webhook 추가 → Forgejo/Gitea:

- **대상 URL**: 이전 단계의 Webhook URL.
- **HTTP 메서드** `POST`, **콘텐츠 유형** `application/json`.
- **secret**: Webhook secret(`X-Gitea-Signature` HMAC 검증에 사용).
- **트리거 이벤트**: **Pull Request**를 선택하고 CI를 미러링하려면 **Commit Status**도 선택합니다.

</Tab>
<Tab value="GitLab" id="gitlab">

Multica에서 GitLab 프로젝트를 추가하면 **Merge request events**, **Pipeline events**, **Job events**, **Comments**(GitLab Note 이벤트)를 포함하는 프로젝트 Webhook 생성을 시도합니다. 생성이나 업데이트가 실패하면 프로젝트에 Hook 상태와 이유가 표시됩니다. 표시된 URL과 secret을 사용해 수동으로 설정할 수 있습니다.

설정 → Webhooks:

- **URL**: GitLab 연결에 해당하는 Webhook URL.
- **Secret token**: 해당 Webhook secret.
- **트리거**: **Merge request events**, **Pipeline events**, **Job events**, **Comments**를 활성화합니다.

`read_api`는 읽기 전용이므로 프로젝트 Webhook을 만들거나 수정할 수 없습니다. 자동 Hook 관리는 `api` scope와 프로젝트 Webhook을 관리할 수 있는 GitLab 역할(Administrator, Maintainer 또는 Owner)이 필요합니다. 그룹 Hook에는 GitLab 관리자 또는 그룹 Owner 권한이 필요하고, System Hook은 GitLab 인스턴스 관리자만 관리할 수 있습니다. 권한이 없으면 해당 관리자가 Hook을 직접 설정하고 검증해야 합니다.

</Tab>
</Tabs>

GitLab 관리자는 인스턴스 전체에 적용되는 [System Hook](https://docs.gitlab.com/administration/system_hooks)을 설정하고 merge request 이벤트를 활성화할 수 있습니다. System Hook만으로 Pipeline, Job, Note 이벤트를 제공한다고 가정하지 마세요. 실제 전달을 확인하고 필요한 이벤트가 빠지면 프로젝트/그룹 Hook으로 보완하세요. Multica는 이 워크스페이스의 GitLab 프로젝트 바인딩에 명시되어 있고 연결된 인스턴스에 속하며 연결 token으로 읽을 수 있는 프로젝트 이벤트만 처리합니다. System Hook으로 다른 프로젝트나 워크스페이스에 대한 접근 권한이 확대되지는 않습니다. 적용 가능한 Hook 조합이 각 프로젝트에 필요한 전체 이벤트를 제공하는지 확인하고, 모든 Hook 유형이 네 가지 이벤트를 모두 전달한다고 기대하지 마세요. 모든 delivery는 저장된 secret으로 인증합니다.

## 미러링되는 내용

- **Pull / Merge Request** — 상태, 작성자, 브랜치, diff 통계, 승인 및 승인 규칙, 토론과 해결되지 않은 댓글.
- **태스크 연결** — 제목이나 브랜치의 태스크 번호로 PR을 연결하며, 본문의 번호는 종료 키워드 바로 뒤에 있을 때만 연결됩니다. 본문에서 단순히 언급하는 것만으로는 연결되지 않습니다. GitHub와 자체 호스팅 코드 호스팅에서 연결된 PR이 모두 merge되면 [GitHub](/github-integration)와 같은 설정 및 규칙에 따라 태스크를 워크스페이스에서 선택한 상태로 옮깁니다.
- **CI** — GitLab MR의 현재 head에 해당하는 Pipeline 및 Job 상태를 Forgejo/Gitea commit status와 함께 표시합니다. 알 수 없는 상태, 이전 head, 실행 중인 Pipeline은 완료된 것으로 표시하지 않습니다.
- **GitLab 상세 정보** — Pipeline과 Job, 범위가 제한된 실패 로그 요약, 기존 접근 권한 검사를 통과한 artifact 링크를 표시합니다. 전체 로그와 artifact 내용은 데이터베이스에 복사하지 않습니다.
- **Wakeup** — 연결된 GitLab MR의 merge, 현재 head의 CI 종료 또는 충돌 감지로 태스크를 깨울 수 있습니다. 채팅 wakeup은 지정한 MR의 merge, close, 현재 head CI 종료를 기다릴 수 있습니다. 자세한 내용은 [태스크 wakeup](/issue-wakeups)을 참고하세요.

태스크에서 **Refresh**를 사용해 MR을 새로고침하거나, GitLab 프로젝트를 새로고침해 해당 프로젝트에서 이미 미러링된 MR을 업데이트할 수 있습니다. 프로젝트 새로고침이 과거의 모든 MR을 발견하는 것은 아닙니다. MR 병합은 연결 token의 GitLab 권한을 사용하며 실패가 명확하게 표시됩니다.

## 에이전트의 Pull Request 생성

PR을 만드는 데 Multica의 Git 코드 호스팅 설정은 필요하지 않습니다. 에이전트는 런타임에서 저장소를 checkout하고 런타임 host 자체의 Git 자격 증명으로 브랜치를 push하고 PR을 만듭니다. 에이전트가 특정 코드 호스팅에서 작업하게 하려면 SSH deploy key 또는 host의 Git credential helper에 저장된 token 등을 사용해 데몬 host가 해당 서비스에 인증할 수 있게 하고 평소처럼 저장소 URL을 추가하세요. 저장소 checkout은 모든 Git URL을 지원하므로 제공자별 설정이 필요하지 않습니다.

## GitLab 연결 및 프로젝트

**설정 → 코드 → Code hosting → 셀프 호스팅 Git**에서 워크스페이스 소유자와 관리자는 여러 GitLab 인스턴스를 연결하고 각 연결에 여러 프로젝트를 추가할 수 있습니다. 인스턴스 base URL에는 하위 경로가 있으면 포함하고, 프로젝트 경로에는 모든 하위 그룹을 포함하세요. 다른 워크스페이스가 같은 인스턴스에 연결해도 token과 프로젝트 목록은 별도입니다.
선택적으로 `GITLAB_PROXY_URL`을 설정하면 GitLab 토큰 검증, 프로젝트 및 Webhook 관리, MR 상세 정보, wakeup 상태 조회 요청을 outbound proxy로 보냅니다. 설정하지 않으면 직접 연결하며 다른 제공자에는 영향을 주지 않습니다.

프로젝트를 추가할 때 Multica는 연결 token으로 프로젝트를 읽을 수 있는지 확인하고 MR, Pipeline, Job, Note Hook 등록을 시도합니다. Hook 상태와 실패 원인이 표시됩니다. `read_api` token은 GitLab 데이터를 읽을 수 있지만 Hook을 만들거나 수정할 수 없습니다. `api` scope와 프로젝트 Hook 관리 권한이 있는 역할을 사용하거나, GitLab 관리자에게 프로젝트, 그룹 또는 System Hook을 설정해 달라고 요청하세요. System Hook 이벤트에도 워크스페이스 프로젝트 허용 목록과 token 읽기 권한 검사가 적용됩니다.

프로젝트를 제거하면 해당 바인딩을 더 이상 사용하지 않습니다. 프로젝트 새로고침은 로컬에 이미 미러링된 MR을 갱신하며 모든 과거 MR을 찾는다고 보장하지 않습니다.

## 기존 GitLab 연동 업그레이드

GitLab 전환은 일반 데이터베이스 마이그레이션이 아니라 유지보수 절차입니다. 업그레이드 전에 데이터베이스와 현재 애플리케이션 버전을 백업하고 `MULTICA_VCS_SECRET_KEY`를 보존하며 연결, 프로젝트, 관리되는 Hook과 수동 Hook을 목록화하세요. 관련 GitLab token이 프로젝트를 읽을 수 있는지 확인하세요. token이나 Webhook secret을 로그에 남기지 마세요.

일반 스키마 마이그레이션은 통합 VCS 테이블과 마이그레이션 원장 테이블만 만들며 기존 GitLab 테이블이나 데이터를 삭제하거나 다시 쓰지 않습니다. 마이그레이션 전에 기존 애플리케이션과 wakeup worker를 중지하세요. `server/` 디렉터리에서 `DATABASE_URL`을 설정하고, 기존 GitLab 데이터가 있다면 `preflight` 전에 `MULTICA_VCS_INTEGRATION_ENABLED=true`, `MULTICA_VCS_SECRET_KEY`, 절대 HTTP(S) 공개 URL(`MULTICA_PUBLIC_URL` 또는 `--public-url URL`)도 설정합니다. 그런 다음 실행합니다.

```sh
go run ./cmd/migrate up
go run ./cmd/gitlab-vcs-migrate preflight
```

`preflight`는 읽기 전용으로 기존 자격 증명, 프로젝트 매핑, 충돌, Hook 목록을 확인합니다. JSON은 비밀 값을 노출하지 않으며 `legacy_pipelines`를 포함한 개수와 점검 결과를 보고합니다. 결과가 `no_op: true`이면 가져올 기존 GitLab 데이터가 없으므로 기존 자격 증명, 키, Hook 단계를 포함한 전환을 건너뜁니다. 자체 호스팅 VCS를 활성화한다면 일반 `MULTICA_VCS_SECRET_KEY`는 여전히 필요합니다. 그 외에는 모든 문제를 해결한 뒤 진행하고 마이그레이션이 끝날 때까지 기존 자격 증명과 복호화 키를 보존하세요. 암호화된 기존 자격 증명이 우선합니다. 해당 저장 자격 증명이 암호화되지 않은 경우에만 정확히 일치하는 기존 인스턴스의 선택적 환경 대체값으로 `GITLAB_BASE_URL`, `GITLAB_TOKEN`, `GITLAB_WEBHOOK_SECRET`을 사용할 수 있습니다. 모든 CLI 명령에는 `DATABASE_URL`이 필요합니다. `--public-url URL`로 `MULTICA_PUBLIC_URL`을 덮어쓸 수 있습니다.
스키마 마이그레이션 전에 실행하면 cutover 전용 테이블, 열, 인덱스 marker가 모두 없는 경우에만 `preflight`가 `state`를 `not_initialized`로 보고하고 점검을 계속합니다. 일부 marker만 있으면 fail closed 처리합니다. `status`에는 마이그레이션 상태 테이블과 delivery 테이블이 여전히 필요합니다.

사전 점검에 문제가 없으면 유지보수 상태에 들어가 단일 트랜잭션으로 기존 데이터를 가져옵니다.

```sh
go run ./cmd/gitlab-vcs-migrate begin
go run ./cmd/gitlab-vcs-migrate migrate
```

`migrate`는 사전 점검을 다시 실행해 기존 테이블을 삭제하지 않고 VCS 데이터를 단일 트랜잭션으로 가져옵니다. 기존 MR 연결, 태스크/채팅 wakeup 대상과 CI 기준은 같은 MR에 계속 연결되며 이전 Pipeline 결과는 새 CI 이벤트로 취급하지 않습니다. 새 애플리케이션을 유지보수 상태로 배포하고 시작한 다음 관리되는 Hook을 전환합니다.

```sh
go run ./cmd/gitlab-vcs-migrate switch-hooks
```

CLI는 `MULTICA_PUBLIC_URL`로 워크스페이스별 Hook URL을 생성하며 `--public-url URL`로 덮어쓸 수 있습니다. 수동 프로젝트, 그룹 또는 System Hook이 없거나 업데이트 권한이 없으면 이 단계가 실패하므로 서비스는 유지보수 상태를 유지해야 합니다. GitLab 관리자가 도구가 출력한 정확한 워크스페이스별 URL로 Hook을 설정하고 제어된 검증 이벤트를 보낸 다음 전환을 다시 실행하세요. `read_api`만으로는 관리되는 Hook을 업데이트할 수 없습니다. 구성된 Hook 전체에서 각 프로젝트의 필수 이벤트 범위를 확인하세요. System Hook이 Pipeline, Job, Note 이벤트를 전달하거나 단일 Hook 유형이 네 가지 이벤트를 모두 전달한다고 가정하지 마세요.

단일 GitLab 인스턴스에 대해 명시적으로 승인된 일회성 예외에는 `MULTICA_GITLAB_SYSTEM_HOOKS_ATTESTED=https://gitlab.example.com`을 제공하세요(CLI: `--attest-no-legacy-system-hooks-for=https://gitlab.example.com`). 경로, 계정 정보, query, fragment가 없는 전체 HTTPS origin만 지정해야 하며 포트를 포함해 정확히 일치합니다. 해당 인스턴스의 `GET /hooks`가 `403`을 반환할 때만 System Hook 인벤토리를 건너뛸 수 있고, 확인은 감사 기록과 복구 상태에 저장되어 재시도에 재사용됩니다. `403`은 권한 문제이지 System Hook 미지원의 증거가 아닙니다. 권한을 수정하거나 다른 origin/오류에 적용되지 않으며 프로젝트/그룹 Hook 인벤토리, 실제 전달 검증, 복구 가능한 Hook, 워크스페이스 격리 또는 유지보수 게이트를 면제하지 않습니다. 일회성 입력이며 `.env`에 영구 저장하지 마세요.

유지보수 중에는 서명 및 권한 검증을 통과한 GitLab Webhook만 receipt로 영구 저장한 뒤 GitLab이 재시도하도록 의도적으로 HTTP 503을 반환합니다. 저장된 receipt가 전달 확인을 뜻하지는 않습니다. 유지보수 창의 UTC 기준 시각을 기록하고 replay와 검증에 같은 값을 사용하세요. `--since`는 이 두 명령에서만 필수이며 `Z`로 끝나는 유효한 RFC3339 UTC timestamp여야 합니다.

```sh
CUTOVER_SINCE="2026-06-12T09:00:00Z" # 이 전환에서 기록한 UTC 기준 시각으로 바꾸세요.
go run ./cmd/gitlab-vcs-migrate replay --since "$CUTOVER_SINCE"
go run ./cmd/gitlab-vcs-migrate verify-hooks --since "$CUTOVER_SINCE"
```

`replay`는 저장된 유지보수 receipt를 GitLab 권위 상태 동기화 경로로 처리합니다. GitLab에 이벤트를 다시 보내지 않으며 저장되지 않은 전달을 복구할 수도 없습니다. `verify-hooks`는 Hook URL, 기준 시각 이후 활성화된 이벤트의 실제 조정된 전달, 각 프로젝트의 MR, Pipeline, Job, Note 전체 범위를 확인합니다. replay, 검증 또는 이벤트 범위 확인이 실패하면 유지보수 상태를 유지하고 Hook/전달 문제를 해결한 뒤 같은 릴리스 버전과 기준 시각으로 다시 실행하세요. 검사가 보류 중이면 최종 완료하지 마세요.

검증에 성공한 뒤에만 최종 완료하고 마이그레이션 상태를 확인합니다.

```sh
go run ./cmd/gitlab-vcs-migrate finalize
go run ./cmd/gitlab-vcs-migrate status
```

`status`가 `phase: "complete"`과 `maintenance_mode: false`를 보고한 뒤에만 정상 쓰기를 재개하세요. 최종 완료는 마이그레이션 잠금 안에서 모든 구성된 Hook이 검증되었고 모든 receipt가 대조되었는지 확인한 뒤 기존 테이블과 롤백 스냅샷을 삭제하고 receipt payload를 지웁니다. 최종 완료 후에는 `restore`로 복구할 수 없습니다.

최종 완료 전에 전환을 중단하려면 유지보수 상태를 유지하고 모든 writer를 중지한 경우에만 복원하세요.

```sh
go run ./cmd/gitlab-vcs-migrate restore
go run ./cmd/gitlab-vcs-migrate status
```

`restore`는 각 Hook의 기록된 원래 설정과 secret을 먼저 복원한 다음 마이그레이션 전에 기록한 데이터베이스 스냅샷을 복원합니다. 성공 후 `status`는 `phase: "restored"`를 보고하지만 `maintenance_mode`는 `true`로 유지됩니다. 애플리케이션 바이너리나 전체 데이터베이스 백업은 복원하지 않습니다. 릴리스 복구 절차가 이전 애플리케이션 artifact를 별도로 복원합니다. Hook 또는 데이터베이스 복원이 실패하면 상태가 `restore_blocked`가 되고 유지보수 상태가 유지됩니다. 해당 상태나 복원 결과를 확인할 수 없으면 서비스를 중지한 채 두고 이전 애플리케이션이나 writer를 시작하지 마세요. 전체 백업으로 새 쓰기를 덮어쓰지 마세요.

최종 완료 또는 이전 서비스 복원 후에는 유지보수 중 발생한 모든 HTTP 503에 대해 GitLab의 전체 전달 기록을 확인하세요. 마이그레이션 도구가 보존한 `recovery_delivery_ids`는 저장된 receipt를 찾는 데 도움이 되지만 전체 전달 기록은 아닙니다. 실패한 전달을 재전송하고 복구할 수 없는 것은 명시적으로 확인한 뒤 현재 권위 MR/Pipeline 상태를 동기화하세요. 데이터베이스 스냅샷이나 `replay`로 저장되지 않았거나 GitLab이 더 이상 재전송할 수 없는 이벤트를 복구할 수 없습니다. 확인되지 않은 이벤트는 보고하고 상태를 추측하거나 wakeup 실행에 사용하지 마세요.
