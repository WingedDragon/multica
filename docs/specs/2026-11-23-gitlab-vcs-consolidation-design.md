# GitLab 集成统一与迁移

## 用户原始需求

1. 「现在已经有了官方实现的自托管支持，我们自行实现的 gitlab 集成是不是没用了(官方自托管不支持的可以从自行实现的功能上迁移过去)」。
2. 补充范围：「给一个完整的功能 迁移、自实现删除设计(准备一次性全部完成)」。
3. 确认 GitLab 连接按工作区分别配置和授权；不同工作区可以连接同一实例，各自控制令牌和项目范围。
4. 确认以官方自托管 VCS 为唯一主干，一次发布完成能力和数据迁移；保留现有功能、权限及唤醒，删除独立实现。必要时保留旧客户端 API 的边界转接；Webhook 权限不足或连接冲突时暂停并由管理员处理。
5. 本次发布中，用户确认一个已授权实例不存在指向旧 Multica 的 System Hook，仅授权在该实例 System Hook 清单因 HTTP 403 不可读取时，使用该单个 origin 的一次性、可审计 operator attestation 跳过该项盘点。域名已脱敏；本次执行只传用户确认的 origin，其他实例未获授权，不得传入确认。此确认不适用于其他 origin 或其他错误，不跳过真实投递核验，也不绕过维护门禁。
6. 本次生产发布补充：「现在没人用，根本不用担心收发漏掉的问题」。本次停机切换可仅核对 Hook 配置，不要求为验证制造维护期投递；此决定替代第 5 条中本次发布必须真实投递核验的限制，不改变 System Hook 盘点确认范围。

## 目标与边界

以官方自托管 VCS 的连接、项目和 PR 处理路径为基础，提供一个完整的 GitLab 集成。一个工作区可连接多个 GitLab 实例，并为每个实例管理多个项目；其他工作区不会因为连接相同实例而获得其令牌或项目访问权。设置页只显示一个 GitLab 接入入口。

本次一次性交付功能迁移、已有数据迁移、受影响的 API 和客户端适配、切换工具、文档及旧独立实现清理。GitHub、Forgejo 和 Gitea 的现有行为不变。GitLab Issue 双向同步、GitLab OAuth 和跨工作区共享凭据不在范围内。

本规格补充 [GitLab 事件与聊天唤醒](2026-11-23-gitlab-wakeups-design.md)，不降低其中的身份、权限、CI 基线、失败及恢复承诺。历史来源为 `docs/superpowers/specs/2026-07-06-gitlab-complete-integration-design.md`；其独立 GitLab 数据模型和不合并共享模型的架构决定由本规格替代，其仍在使用的产品能力由本规格承接。

## 统一后的功能

### 连接和项目

- 复用 VCS 连接模型、加密存储和工作区权限。所有者和管理员管理连接和项目，成员只能读取自己工作区允许的内容。保留实例完整基础 URL（包括子路径）和多级 group；以工作区、实例和 GitLab 项目身份区分对象。
- 保留 GitLab 项目输入、校验、添加、移除、刷新、连接状态和 Webhook 状态。添加项目时按现有行为登记仓库地址并尝试自动创建项目 Webhook；保留手动配置及可见的失败原因。项目刷新覆盖本地已镜像的 MR，不承诺发现全部历史 MR。
- 保留项目 Webhook 的 MR、Pipeline、Job、Note 事件，以及官方已有的手动项目、群组和 System Hook 接入。System Hook 的项目 allowlist 和令牌可读性检查不放宽；其他事件继续遵守原有连接、项目和工作区的访问边界。重复投递不得重复建立关联、推进任务或触发唤醒。
- 延续 GitLab 的 `GITLAB_PROXY_URL` 行为，使统一入口的令牌校验、项目管理、Webhook 管理、MR 详情和唤醒读取都使用同一代理配置；其他提供方不受影响。令牌和 Webhook 密钥不进入日志或响应，除现有连接或轮换流程明确的一次性展示外不再次显示。

### MR、CI 和操作

- 保留现有 MR 状态、变更统计、审批及审批规则、讨论与未解决评论、Pipeline 和 Job、失败日志摘要及制品入口。日志读取有界，制品按现有权限检查后提供，不把完整日志或制品写入数据库。
- 保留任务页面手动刷新 MR、项目刷新和合并 MR；合并使用连接令牌的 GitLab 权限，失败时明确显示，不伪造成功。保持已有的刷新诊断、事件更新、排序及状态可见性。
- GitLab Pipeline 状态接入统一 PR 列表当前 head 的检查展示；按实例、项目、MR、head 和 Pipeline 身份隔离，fork 和重跑遵守现有唤醒规格。不能把未知、旧 head 或仍运行的 Pipeline 显示为已完成。
- 保留原 GitLab 标题、描述、分支中的任务关联和关闭意图，以及原官方 VCS 的自动关联、手动关联/解除和工作区 PR 自动完成规则。迁移前各自形成的关联和自动完成语义继续有效；同一任务混有多种来源时，不能因迁移或去重而提前关闭任务。GitHub 行为保持不变。
- 原 GitLab 任务唤醒和聊天唤醒迁入统一 MR 来源，保留目标、状态、期限、指纹、去重和 CI 基线。迁移、重新同步或同一 Pipeline 重复投递不能导致旧结果误触发；符合条件的新结果仍可触发。

## 数据与接口

### 单一事实来源

统一连接、项目绑定、PR/MR、任务关联和 Pipeline 状态以 VCS 路径为唯一事实来源。GitLab 特有的审批、讨论、Job、日志摘要和制品元数据可以保留专用结构，但须引用统一 MR 身份，不再维护第二套独立 MR 镜像或另一套关联与唤醒判断。GitLab 特有客户端和解析代码可作为统一 provider 的实现细节复用；删除的是独立产品入口及重复数据和业务链路，不要求删除仍被统一 provider 使用的 GitLab 协议代码。

迁移保留现有连接凭据、项目绑定和 Webhook 管理信息、MR 字段及关联来源、关闭意图、审批、讨论、Pipeline、Job、刷新诊断、任务关联、聊天与任务唤醒的目标及基线。MR 以工作区、完整实例地址、完整项目路径和项目内编号核对；同名项目和同号 MR 在不同实例或工作区不能合并。已有官方 VCS 数据同样保留，相同实体合并时保留双方关联与最新有效状态，字段和事件版本不得倒退。迁移不因旧缓存被导入而执行任务状态变化或唤醒。

旧连接 ID 和 MR ID 若已被公开 API、CLI 或已保存条件引用，迁移后仍须解析到原目标；优先沿用原 ID，遇到统一记录冲突时，以受工作区约束的旧 ID 到统一 ID 映射解决。映射只用于边界解析，不形成第二套连接或镜像。无法无歧义建立映射时停止切换，列出冲突供管理员处理，不凭项目名称或编号猜测。

### API 与客户端

统一 UI 和新 API 使用 VCS 入口；已有桌面客户端可继续读取和操作其此前受支持的 GitLab API 和响应形状。为此保留必要的旧公开 API 边界转接，由统一实现完成授权和操作；不保留旧业务处理链、双写或旧表。旧客户端看不到新功能不影响既有功能和权限。GitLab 聊天唤醒 CLI 的已发布语法和已保存连接引用继续可用，GitHub API 和 CLI 不变。

现有 `/api/webhooks/gitlab` 及连接级旧 Webhook 地址属于切换对象：迁移时将受管理项目 Hook 更新到统一 VCS Webhook 地址，验证成功后移除旧接收路径。手动配置的项目、群组或 System Hook 由管理员更新并验证；未完成时不能宣告切换成功。设置页和文档只展示统一接入路径。

**实例能力与 Hook 权限判定。** 能力按连接所属的 GitLab 实例判定，而不是用一次实例结果套用全部连接。Group Webhooks 仅 Premium/Ultimate 支持且需要该 group 的 Owner 或实例管理员；已认证的 `/metadata` 明确返回 `plan=free` 或 `enterprise=false` 时可禁用该实例的 Group Hook 盘点，项目级功能仍继续工作。若 Group Hook API 返回 404，只有在本连接已确认对现存 group 具有 Owner/管理员权限时，才可将该 group Hook 能力判为不可用；否则 404、403、不可读的祖先 group、超时及其他错误均为权限不足或未知，必须阻止切换并保留旧 Hook。System Hooks 属于 Free+，但仅实例管理员可读；403 是权限结果而非功能不存在，默认阻止切换。唯一例外是操作人显式确认一个完整 HTTPS 实例 origin 后，对该 origin 的 `GET /hooks` 明确返回 403 时跳过该实例的 System Hook 清单盘点，并将 origin 与迁移代次、操作人写入审计及可恢复状态。origin 必须精确匹配（含端口），不能含路径、账号、query 或 fragment；该确认不作用于任何其他 host/port、状态码或 API，也不改变 Hook 恢复、工作区隔离或维护门禁。投递验证遵循下方的默认模式或第 6 条确认的停机模式。参见 [Group webhooks API](https://docs.gitlab.com/api/group_webhooks/) 与 [System hooks API](https://docs.gitlab.com/api/system_hooks/)。


## 一次性切换与恢复

一次发布不等于把远程 GitLab 操作和数据库变更当作一个事务。发布工具必须提供可检查、可重入的迁移流程，并记录每项操作的身份和完成状态，不记录密钥。执行期间暂停用户业务写入和后台唤醒处理，只允许迁移、受控 Webhook 验证和权威状态同步所需的写入；在完成验证或恢复之前不开放正常写入。

1. **盘点和预检。** 备份数据库及当前应用版本；盘点两个来源的连接、凭据、项目、Hook、MR、关联和活跃唤醒。检查加密密钥、实例连通性、项目权限、数据映射、Webhook 地址、受管理 Hook 的修改权限及人工 Hook 清单。环境变量提供凭据的旧连接按原实例精确匹配，将凭据加密迁入对应工作区连接；缺少凭据或解密失败则停止。令牌、密钥不打印。相同工作区/实例的连接或凭据不能无歧义合并时先停止并处理。预检及重试只可在显式传入 `--attest-no-legacy-system-hooks-for=https://gitlab.example.com`（示例 origin）时，对单个精确 origin 应用一次性确认；确认及迁移代次写入审计，恢复状态保留该精确 origin，不写入永久配置。
2. **准备统一入口。** 保留旧数据库和 Hook 的可恢复记录，准备新版本及受管理 Hook 的新地址和认证信息；对手工 Hook 给管理员明确的目标和验证步骤。仅有 `read_api` 等只读权限的令牌不假设能创建或修改 Hook；缺少写权限时等待管理员处理。验证远程修改不会影响其他工作区或无关 Hook。
3. **事务迁移。** 在独占维护窗口内，将旧数据和已有 VCS 数据按映射迁入唯一模型，同时改写持久化引用和建立必要的旧 ID 边界映射。校验记录、字段、关联、授权范围和基线；数据库迁移要么全部提交，要么回滚。不得通过常规启动迁移先删除旧表，再依赖后续命令找回凭据或数据。
4. **切换和核对。** 在维护模式启动统一 Webhook 接收端，更新受管理项目 Hook；管理员更新其他涉及的 Hook。逐项验证 URL、密钥和所需事件确实投递到正确工作区及项目；验证与同步不得推进任务或触发唤醒。维护期真实事件在验签和权限校验后持久化收据，并返回 `503`，使 GitLab 将其标记为失败投递；不得确认后丢弃。对已知 MR 和活跃唤醒从 GitLab 权威状态重新同步，并核对维护窗口内的 GitLab 投递记录；未确认的项目保持未完成状态，不开放正常写入。同步不把旧 CI 结果当成新事件，也不因重放产生重复效果。
   对操作人确认无业务使用的停机切换，可在 `verify-hooks` 显式传入 `--configuration-only`，以实际 Hook URL 和事件开关核对替代逐类投递证据；已接收的收据仍先完成对账。发布脚本仅在本地明确设置 `MULTICA_GITLAB_CONFIGURATION_ONLY=1` 时使用该模式，默认仍要求真实投递。此模式不证明运行时投递或维护期事件完整性。
5. **完成或恢复。** 所有映射、Hook、数据和活跃唤醒验证通过后，删除旧独立表、旧处理链及旧 Webhook 路由，启用统一服务。完成前失败时保持维护状态，以记录恢复修改过的 Hook 和数据库/应用版本，再核对旧路径可用。恢复或重试均不得泄露凭据或清除无关数据。开放写入之后，不自动用全库备份覆盖新写入；后续问题按前向修复或经管理员决定的数据恢复处理。

Webhook 是外部系统，数据库备份不能保证还原切换期间未送达、且 GitLab 已无法重投的瞬时事件。GitLab 13.12 对 503 会退避，不能假设自动重投。核对可用投递记录、处理已知失败事件并重新同步当前权威状态；无法确认的事件须报告管理员，不能宣称完整接收或用猜测状态触发唤醒。

## 可观察验收

以下验收覆盖需求 1–6，且不替代 GitLab 唤醒现行规格的全部验收。

1. 一个工作区连接两个 GitLab 实例并分别添加多级 group 项目；另一个工作区无相应授权时无法读取项目、MR、日志或使用其令牌。相同实例在不同工作区分别连接，互不改变配置。
2. 项目添加后可看到连接和 Hook 状态；具备权限时自动注册 MR、Pipeline、Job、Note Hook，权限不足时可见失败并可手工完成。项目移除、刷新和代理连接沿用原行为；System Hook 只影响已配置且令牌可读的项目。
3. 同一 MR 通过统一列表显示一次，包含正确状态、当前 head CI、审批、讨论、Job、日志及制品；刷新与合并实际调用对应 GitLab 实例，其他工作区不能访问。重复事件和旧事件不回退状态或造成重复关联。
4. GitLab 任务关联、关闭意图和既有自动完成规则，及官方 VCS 的关联和自动完成规则在迁移前后保持各自效果；混合 GitHub/GitLab/其他 VCS 的任务不会因为迁移提前完成。GitHub、Forgejo、Gitea 现有行为不变。
5. 使用含多实例、同路径同号 MR、旧和官方 VCS 重复实体、已有关联及完整详情的数据库迁移，逐项核对连接、项目、MR、字段、关联、凭据、审批、讨论、Pipeline、Job 和诊断；重复运行不会重复写入。冲突或缺少凭据时停止且不丢数据、不扩大权限。
6. 迁移前已存在的任务与聊天唤醒在迁移后仍绑定原目标、保留期限和 CI 基线；旧结果不误触发，同 head 的新 Pipeline 终态仍可触发，暂时无法同步时继续等待并显示原因。旧连接 ID 的 CLI/API 请求仍定位原目标；跨工作区 ID 不能访问。
7. 已安装的旧桌面客户端通过原公开 GitLab API 继续完成此前受支持的操作；新版只有一个 GitLab 入口，统一后端不存在独立 GitLab 连接、MR 镜像、关联或双写路径。旧项目 Hook 已切至统一接收路径，旧 Webhook 路由移除。
8. 模拟 Hook 修改失败、手动 Hook 尚未配置、数据库迁移失败、服务中断及重试：维护窗口内不开放未完成的集成，恢复后旧版本与 Hook 可用，重试不重复处理；开放写入后不会自动回滚覆盖新数据。确认 Free 计划或 Community Edition 会禁用 Group Hooks 盘点但保留项目 Hook 功能；Group Hook API 返回 404 只有在本连接已确认 group Owner/实例管理员后才视为该 scope 不支持。403、祖先 group 不可见、Owner/管理员权限未知及未受 attestation 覆盖的 System Hook 403 均阻止切换，旧 Hook 和事件不得被静默跳过。
9. 同步更新受影响的所有语言文档、部署配置说明和升级步骤；明确工作区隔离、令牌权限、代理、Webhook 和迁移中需要管理员操作的条件。
10. System Hook 盘点特例只针对命令显式确认的单个完整 HTTPS origin：仅当该实例 `GET /hooks` 返回 403 时生效，按精确 host 与 port 匹配；审计关联迁移代次与 operator 身份，并在恢复/重试中复用。直接命令示例为 `--attest-no-legacy-system-hooks-for=https://gitlab.example.com`。路径、账号、query、fragment 无效；其他主机/端口、状态码、权限/网络异常和项目/群组 Hook 盘点照常阻止。旧 Hook 仍可恢复且作用范围隔离，维护门禁仍须通过。Release 接受本地一次性输入，不在命令行传递密钥或写永久配置，并安全传至预检和迁移开始。本次仅传用户明确确认的一个 origin，其他实例不传。
11. 第 6 条确认的停机发布显式使用配置核对模式；核对每个项目的 Hook URL、事件开关、数据迁移和服务状态，报告维护期投递未逐类验证。默认模式仍要求真实投递，未对账的已接收收据仍阻止完成。
