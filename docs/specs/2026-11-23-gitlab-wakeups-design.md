# GitLab 事件与聊天唤醒

## 用户原始需求

1. 「现在任务唤醒是支持 GITHUB 的，是否可以适配上 GITLAB， 让 GITLAB 对当前的 GITHUB 功能对等」
2. 补充并明确范围：「什么vcs 托管环境？跟着有啥关系？我要的是事件/聊天唤醒」
3. 确认：对任务唤醒支持关联 GitLab MR 合并、CI 结束和冲突；对聊天唤醒支持指定 GitLab MR 合并、关闭和 CI 结束。沿用各自现有触发、超时和权限语义，复用现有 GitLab 接入；以 GitLab 连接、完整项目路径和 MR 编号区分目标，支持多级 group。CI 等待创建后的新结果，暂时无法获取状态时继续等待并显示原因。

## 目标与范围

让 GitLab merge request（MR）可用于任务事件唤醒和聊天唤醒中与 GitHub pull request（PR）对应的条件。复用工作区已有 GitLab 集成、MR 关联和 Pipeline 数据；不改变 GitHub 规则的行为，也不扩展自动化 webhook 的功能。

任务唤醒关注当前任务直接关联的 MR；聊天唤醒关注明确指定的 MR，不要求其关联任务。唤醒产生的运行、通知、管理、频率限制、权限复查和超时处理沿用各自现有机制。

## 设计

### 任务事件唤醒

现有「关联 PR」条件同时评估直接关联的 GitHub PR 和 GitLab MR；任何一个满足条件即可唤醒：

- **合并**：MR 已合并即满足，创建或重新启用时已满足的条件也会触发。
- **CI 结束**：评估 MR 当前 head 对应的 Pipeline 结果，成功或失败均为结束；没有结果或仍在运行时继续等待。创建或重新启用时建立基线，等待之后的新结果，沿用现有 GitHub 条件语义。
- **出现冲突**：获取 MR 当前 head 的合并冲突判断；有冲突即满足，创建或重新启用时已满足的条件也会触发。未知或尚在计算的结果不是冲突，也不是冲突已解决。旧 head 的判断不能用于新 head。

继续沿用条件指纹及重复规则语义：不同 MR 即使编号相同也须独立识别；同一 MR 的冲突判定暂时未知后恢复，不应凭空产生新一次触发。

### 聊天唤醒

智能体可指定工作区已接入且已镜像的 GitLab MR，等待：

- **合并**：MR 已合并。
- **关闭**：MR 已关闭或已合并，与 GitHub 的关闭条件一致。
- **CI 结束**：MR 当前 head 的 Pipeline 成功或失败；创建或更新唤醒时建立基线，等待之后的新结果。

CI 基线记录 Pipeline 的稳定身份及终态版本，而不只是 head 和成功／失败：同一 head 上重新运行且得到相同结果时，新的结果仍须可识别。任务与聊天唤醒均采用此基线。基线暂时不可用时，使用规则生效时间区分之前和之后的结果，不能把恢复后发现的旧结果当作新结果。

合并和关闭在创建时已成立则按现有条件检查流程触发。聊天唤醒仍在原对话发起新一轮运行，沿用默认 24 小时、最长 7 天的条件等待和到期汇报规则。唤醒信息及结果应指出 GitLab 项目、MR 和观察到的状态，让智能体能明确报告。

### MR 身份与接口

GitLab MR 使用工作区内的 GitLab 连接标识、完整项目路径（包括所有 subgroup）和项目内 MR 编号定位；不同实例、连接或项目的同号 MR 不能混淆。创建聊天唤醒时明确选择唯一目标，无法唯一确定时返回可操作的错误，不猜测目标。创建后绑定确定的连接和 MR，后续不会因同名仓库出现而转向其他目标。

扩展聊天唤醒 API 和 `multica chat wakeup` 的输入，使智能体能指定 GitLab 连接、完整项目路径及 MR 编号，并可发现可用语法；返回值及界面展示提供足够信息区分目标。现有 GitHub API 输入、CLI 用法和已保存规则保持原有含义，不将已有 GitHub 规则重新解释为 GitLab。

聊天条件以 `provider: "gitlab"`、`connection_id`、完整项目路径 `repo`、MR `number` 和 `event` 指定目标。CLI 用 `multica chat wakeup connections` 查看工作区连接，用 `--until-pr group/subgroup/project#N[:merged|closed|checks] --gitlab-connection <connection-id>` 创建条件。

### 状态来源与失败行为

MR 与 Pipeline 数据使用现有 GitLab 集成的镜像；冲突判断通过该连接获取并记录，须与 MR 当前 head 关联。工作区、连接和仓库的现有访问边界继续适用，不能通过唤醒读取其他工作区或未授权项目的数据。

MR 状态与 Pipeline 状态分别确认：Pipeline 查询失败或超时不能阻止已确认的 MR 合并、关闭或冲突条件；CI 条件则等待 Pipeline 恢复。MR 状态先持久化，再查询 Pipeline，避免 CI 请求耗尽调用时限后无法保存已取得的 MR 状态。

MR 尚未镜像、连接不可用、Pipeline 尚无结果、冲突状态未知或尚未计算时，不以猜测结果触发；等待期间提供可见的原因，恢复后继续检查。聊天唤醒创建时目标不存在或不唯一，返回明确错误；已创建的目标后来不可用则继续等待，直到恢复或按既有超时规则结束。获取状态失败不等于成功、失败或无冲突。

保持现有 GitHub 与 GitLab 数据隔离，以及现有 webhook 认证、项目访问控制和更新顺序规则。唤醒不新增仓库授权或绕过集成配置。

Pipeline 状态按连接、完整项目身份和 Pipeline 身份隔离；查询只读取目标 MR 的当前 head 对应结果。对来自 fork 的 MR，目标可包括 MR 所在项目的 MR Pipeline，以及权威 MR 指明的来源项目、来源分支和当前 head 对应的分支 Pipeline；其他项目的同 SHA Pipeline 不能混入。系统级 webhook 的 Pipeline 事件和 MR 事件一样，必须通过工作区项目配置及连接的项目可读性检查。以 Pipeline 自身的终态判断是否结束，运行中的 Pipeline 不因其中某项失败而提前算作结束。

镜像写入失败时向 GitLab 返回失败，不能确认接收后丢失更新。等待中的目标需要有基于 GitLab 权威状态的重新同步路径，覆盖事件丢失、连接恢复和状态写入失败；状态尚未确认或同步失败时显示原因并继续等待，不能用已知过期状态触发。重新同步的结果仍遵守目标身份、权限、head 和 CI 基线规则。

## 验收

以下验收对应原始需求 1–3；除 GitLab 扩展外，既有唤醒行为保持不变。

1. 在关联 GitLab MR 的任务上，分别创建合并、CI 结束、冲突唤醒；对应状态满足时启动该任务上的智能体运行。多个关联 MR 中任一满足即可；不关联的 MR 不触发。
2. MR 已合并或已有当前 head 冲突时，新建对应任务唤醒后正常触发；CI 已结束时新建或重新启用 CI 唤醒不会立即以旧结果触发，新结果结束后触发。
3. 冲突判断未知、计算中或属于旧 head 时不触发；同一冲突暂时未知再恢复不重复触发。不同连接或项目的同号 MR 不互相覆盖。
4. 在聊天运行中分别针对 GitLab MR 创建合并、关闭、CI 结束唤醒；满足后在原对话报告。关闭条件对合并或关闭均成立；CI 成功与失败均可触发，创建前的旧结果不触发。
5. 多级 group 项目可被指定；相同项目路径和 MR 编号出现在不同连接时，必须选择唯一目标，不能误唤醒。保存后其他同名目标不会改变监听对象。
6. 未镜像或不唯一的聊天目标创建失败并说明原因；已创建的 MR 状态暂不可用时显示等待原因，恢复后继续，超时按各自既有规则处理。无权访问的项目不能通过唤醒泄露数据。
7. GitHub 已保存规则、现有 API/CLI 用法及对应条件行为不变；任务和聊天唤醒入口、CLI 帮助和受影响的各语言文档说明 GitLab 用法及条件。
8. 同一 head 的 Pipeline 重新运行并得到与基线相同的终态时，新结果可触发；基线暂不可用后恢复时，创建前结束的旧 Pipeline 不触发。Pipeline 仍在运行且某项已失败时不提前触发。
9. 同一连接下两个项目存在相同 commit SHA 时，只用目标项目的 Pipeline；未配置或不可读项目的系统级 Pipeline 事件不能影响唤醒。
10. 模拟 MR 或 Pipeline 镜像写入失败、事件丢失及连接恢复：不能以过期状态误触发；目标状态重新同步后，满足条件的唤醒按规则继续，无法同步时显示原因并按原超时规则处理。
