# Loop 与 Multica 任务同步

## 用户原始需求

1. 「我现在还有一个低版本的 multica 在运行，且我想把上面的任务按需同步过来再这里做，做完再同步过去，使用插件/改实现好支持吗？」
2. 补充：「不是挑选，而是通过映射关系进行相关负责的任务同步/更新等」。
3. 补充：「旧 multica 是指的 octo-loop，底层就是旧版 multica, 映射只需要人映射，然后新版 multica 跑任务，旧版的体现都是人的视角」。
4. 补充：「同步过来的只 pending，启动由我手动进行」；确认使用 `backlog`。
5. 「再 apps 里面加一个独立服务吧，且尽可能少的影响其它服务/公共代码(方便后续跟官方同步/升级)」。
6. 首次同步：「导入映射人员在 Loop 上已有的所有未完成任务」。
7. 回写规则：「Loop 原任务不变，不同步状态」。
8. 确认：独立服务按人员映射导入和持续同步任务需求，Multica 中创建 `backlog` 任务，不自动分配 Agent 或执行；处理进展和结果以评论回写 Loop，不改变 Loop 状态或负责人。
9. 补充：「应该支持单实例，多组关联(一组一个 token + workspace 绑定), 具体绑定使用配置文件即可，当前的 selfhost skill 需要添加部署相关信息，部署到 my-mini 即可，可以使用 superd 管理进程」。

## 设计

在 `apps/` 内运行独立同步服务，通过两端接口访问配置的工作区，人员映射以稳定 ID 指定。服务保存 Loop 与 Multica 的任务及评论关联和同步基线；重启沿用已有记录。首次及后续扫描 Loop 中映射人员的未完成任务。已关联任务持续跟踪；Loop 任务转给未映射的人时停止导入新变化，保留两端任务及同步记录。

同一进程通过配置文件管理多组关联；每组指定 Loop 令牌的环境变量、两端工作区、人员映射及独立状态文件。凭据保存在部署环境中，不写入仓库。各组独立记录同步结果和待核实写入，一组运行失败不阻止其他组。关联部署在 `my-mini`，由用户级 Super 管理。

Loop 的标题和描述向 Multica 同步；两边同一字段自上次同步以来均有变化时报告冲突，不覆盖。Loop 评论及 Multica 处理进展和结果以评论传播，以来源关联避免回声。Loop 保持原有状态和负责人。Multica 新任务以 `backlog` 创建且不指定 Agent；同步更新不得修改其状态或负责人。服务自身的凭据决定回写身份，权限受两端服务约束。

同步记录持久保存。网络或接口错误、歧义写入、无法映射或内容冲突必须可见，不能声称同步成功；可能已经提交但未确认的写入需人工核实后恢复，不盲目重复写入。记录中包含连接及工作区身份，不能把不同实例的任务混为一谈。Loop 评论回写前检查触发预览，避免意外触发专家。

## 验收

- 配置人员映射后首次扫描全部分页，导入符合条件的既有未完成任务，重复运行和重启后不重复创建。
- Multica 新任务为 `backlog` 且未分配 Agent；同步不启动任务。
- Loop 标题、描述及评论变化能够到达关联的 Multica 任务；双向更改冲突时不覆盖。
- Multica 的处理进展及结果能够作为评论回写 Loop；重复扫描不重复发送、不形成回声。
- Loop 状态和负责人不被服务修改；转出映射范围的任务保留。
- API 错误、冲突和结果不确定的写入可见，不通过重复发送掩盖。
- 同一进程使用不同 Loop 令牌同步多组工作区关联，即使任务 ID 相同，各组状态仍独立；一组运行失败不阻止其他组。
